# Подключение оплаты: действия владельца

Интеграция подготовлена для ЮKassa: покупатель открывает защищённую страницу оплаты, платит доступным способом, а бот проверяет результат через API и начисляет токены. Рабочий магазин, реальные ключи, чеки НПД и проверка настоящего платежа требуют настройки владельцем. До завершения подготовки оставь `PAYMENTS_ENABLED=false`.

Инструкция проверена по официальным источникам 9 сентября 2026 года. Тарифы, доступные способы и решение о подключении конкретного проекта определяет ЮKassa.

## Что сделать сначала

1. Подать заявку на подключение ЮKassa как самозанятый. Подготовить ФИО, телефон, почту, реквизиты для получения денег и описание сервиса: персональные цифровые расклады и интерпретации на основе даты и места рождения. Дать модерации действительный адрес проекта и примеры результата. Статус самозанятого сам по себе не означает, что магазин уже подключён. ЮKassa указывает поддержку карт и СБП для самозанятых; конкретные условия нужно получить при подключении. [ЮKassa для самозанятых](https://yookassa.ru/platezhi-dlya-samozanyatyh).
2. Указать ФИО продавца, ИНН и работающий контакт поддержки. Опубликовать условия покупки и политику обработки персональных данных по постоянным HTTPS-ссылкам. В условиях описать содержание продукта, цены, порядок доступа и возвратов. В политике отразить дату, время и место рождения, Telegram ID, хранение данных и фактическое использование ИИ-провайдера, если он включён.
3. Подготовить выдачу чеков через «Мой налог» или выбранного уполномоченного оператора. В этой версии автоматической выдачи и доставки чеков НПД нет. Подробности ниже.
4. Создать отдельного тестового Telegram-бота и отдельную тестовую базу данных. Пройти сценарии из раздела «Проверка» до подключения рабочих ключей.
5. Перевыпустить ранее хранившийся в исходниках токен основного бота в BotFather. Новый токен и секретный ключ ЮKassa хранить только в `.env`/секретах сервера. Не отправлять их в переписку и не добавлять в Git.

## ЮKassa и правила канала продаж

ЮKassa технически поддерживает оплату цифровых услуг самозанятого картами и СБП. У Telegram есть отдельное правило: цифровые товары и услуги, продаваемые внутри ботов и mini apps Telegram, должны оплачиваться через Telegram Stars. Внешняя ссылка на оплату сама по себе не подтверждает исключение из этого правила. Одобрение магазина ЮKassa не заменяет соблюдение правил Telegram. До публичного включения рублёвой оплаты необходимо определить допустимый канал продаж для данного продукта; подготовленный модуль ЮKassa не является подтверждением допустимости рублёвой продажи внутри Telegram. В проекте также есть реализация Stars для соответствующего режима. [Правила Telegram для цифровых товаров](https://core.telegram.org/bots/payments-stars).

## Какой способ выбрать в ЮKassa

| Настройка | Поведение покупателя | Что требуется |
|---|---|---|
| `YOOKASSA_METHOD=auto` | На странице ЮKassa покупатель выбирает карту, СБП или другой доступный способ | Нужные способы должны быть подключены в магазине |
| `YOOKASSA_METHOD=sbp` | Счёт создаётся сразу для СБП | Подключённая СБП и проверка сценария на нужных устройствах |

Для первого запуска удобен `auto`: интерфейс выбора и ввод платёжных данных обслуживает ЮKassa. Бот не получает реквизиты карты. В сценарии «Умный платёж» отображаются способы, подключённые именно к твоему магазину; наличие метода в документации не гарантирует его доступность в конкретном договоре. [Сценарий ЮKassa «Умный платёж»](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/smart-payment).

## Настройки `.env`

Заполняй файл в папке проекта. Секреты в примере намеренно отсутствуют.

| Переменная | Что указать |
|---|---|
| `BOT_TOKEN` | Новый токен того бота, который запускается в этой среде |
| `ADMIN_IDS` | Свой числовой Telegram ID; несколько ID через запятую |
| `DB_PATH` | Путь к базе. Для теста, например, `data/test-users.db`. В рабочей среде — путь к существующей базе пользователей |
| `BRAND_NAME` | Название сервиса |
| `SUPPORT_CONTACT` | Действующий контакт, например, `@имя_поддержки` |
| `SELLER_NAME` | Полные ФИО продавца |
| `SELLER_INN` | ИНН физлица, 12 цифр |
| `TERMS_URL` | Публичная HTTPS-ссылка на условия покупки |
| `PRIVACY_URL` | Публичная HTTPS-ссылка на политику обработки данных |
| `PAYMENTS_ENABLED` | `false` при подготовке; `true` после настройки соответствующей среды |
| `PAYMENT_PROVIDER` | `yookassa` для рублёвого модуля; `stars` для Telegram Stars |
| `YOOKASSA_SHOP_ID` | ID тестового или рабочего магазина, соответствующий ключу |
| `YOOKASSA_SECRET_KEY` | Секретный API-ключ этого магазина |
| `YOOKASSA_TEST` | `true` только для тестового магазина; `false` для рабочего |
| `YOOKASSA_METHOD` | `auto` или `sbp` |
| `PAYMENT_RETURN_URL` | Необязательный HTTPS-адрес возврата; если пусто, бот формирует ссылку на свой Telegram-профиль |

ID магазина находится в «Настройки → Магазин», API-ключ — в «Интеграция → Ключи API». Ключ тестового магазина и ключ рабочего магазина различаются. [Аутентификация ЮKassa](https://yookassa.ru/developers/using-api/interaction-format).

Относительный `DB_PATH` считается от папки проекта. Пустое значение означает `users.db` в папке проекта. Не указывай случайный новый путь в рабочей среде: иначе бот откроет пустую базу вместо существующей. Обновление схемы сохраняет пользователей, баланс и прежний бессрочный доступ к матрице.

После изменения `.env` процесс нужно перезапустить. Для одного рабочего бота запускай один экземпляр приложения. Сервер должен иметь постоянный доступ к Telegram и API ЮKassa.

## Цены, уже записанные в проекте

Пакеты: 10, 50, 100, 200, 250, 500 и 1000 токенов. В рублёвом каталоге действует базовая цена 1 ₽ за токен; для 500 токенов установлена цена 349 ₽, для 1000 — 699 ₽. Это цены до комиссии провайдера и налогов. Каталог хранится на сервере в `commerce.PACKAGES`; сумма не принимается из кнопки пользователя.

| Услуга | Цена в токенах | Доступ |
|---|---:|---|
| Полный расклад | 10 | На выбранный ботом местный день |
| Совместимость | 15 | На день, как в исходной логике проекта |
| Подписка | 199 | 30 дней; полные расклады и совместимость |
| Изображение матрицы | 349 | Для текущей даты рождения |
| Разбор матрицы | 499 | Полный текст и изображение для текущей даты рождения |

Повторное открытие приобретённого материала для той же даты рождения бесплатно. Если изображение уже куплено отдельно, разбор остаётся самостоятельной покупкой за 499 токенов. Старый бессрочный доступ к изображению, выданный до обновления, сохраняется. Активная подписка повторно не списывается; автоматических продлений и автоплатежей нет.

## Проверка в тестовой среде

ЮKassa предоставляет отдельный тестовый магазин и сценарии проверки успешных и неуспешных оплат. Используй тестовые реквизиты из её инструкции, а не настоящую карту наугад. [Тестирование ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).

Для тестового запуска одновременно должны быть отдельный `BOT_TOKEN`, тестовые `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY`, `YOOKASSA_TEST=true` и отдельный `DB_PATH`. Тестовые покупки начисляют обычные внутренние токены в выбранную базу. Поэтому нельзя тестировать на рабочей базе и затем просто переключить `YOOKASSA_TEST=false`.

Проверь последовательно:

1. В `/tokens` видны пакет, точная сумма, продавец, условия и поддержка. Открывается платёжная страница.
2. При успешной тестовой оплате приходит начисление, а заказ появляется в «Мои платежи» и админ-панели.
3. Повторные нажатия «Проверить оплату» не увеличивают баланс повторно. Ссылка возврата из браузера сама не начисляет токены.
4. Неоплаченный или отменённый счёт ничего не начисляет.
5. После перезапуска бота незавершённый заказ остаётся доступным для проверки. Завершившаяся оплата обнаруживается и после перезапуска.
6. Покупка разбора списывает 499 токенов один раз, открывает текст и изображение; повторное открытие бесплатно.
7. Полный возврат из админ-панели возвращает платёж через провайдера и снимает токены ровно один раз. Повторная проверка сохраняет результат.
8. Возврат после расходования части токенов создаёт соответствующий отрицательный баланс. Новые платные покупки блокируются до его пополнения, уже купленные материалы доступны.

Затем останови тестовый процесс, сохрани рабочую базу, настрой отдельную рабочую среду и проведи одну согласованную небольшую реальную покупку с проверкой чека и возврата. Тестовые результаты сами по себе не подтверждают успешную рабочую оплату.

## Чеки НПД: обязательный отдельный процесс

Плательщик НПД освобождён от применения ККТ, но обязан сформировать и передать покупателю чек через «Мой налог» либо уполномоченного оператора/банк. ФНС указывает выдачу чека в момент расчёта наличными или электронными средствами платежа; срок до 9-го числа следующего месяца относится к иным безналичным расчётам и не является общей отсрочкой для всех онлайн-покупок. [ФНС: формирование и передача чеков](https://www.nalog.gov.ru/rn53/news/activities_fts/16643640/).

В этом проекте нет интеграции с API «Мой налог», автоматической регистрации дохода, отправки НПД-чека покупателю и автоматического исправления чека при возврате. Подтверждение оплаты ЮKassa и сообщение бота о начислении токенов не заменяют НПД-чек.

До запуска организуй процедуру: увидеть подтверждённый заказ, сформировать корректный чек на фактически продаваемую услугу, передать его покупателю через заранее определённый канал и сохранить связь «номер заказа → чек». Поддержка должна уметь повторно предоставить чек. Если объём покупок не позволяет делать это вовремя вручную, сначала подключи оператора автоматизации НПД и проверь его отдельно.

После настоящего возврата исправь сведения о доходе в «Мой налог» в соответствии с фактической операцией. Бот этого не делает. У ФНС есть отдельное пояснение об уменьшении доходов при возврате ранее полученной оплаты. [ФНС: возвраты у самозанятых](https://www.nalog.gov.ru/rn71/news/activities_fts/10972997/).

## Возвраты и ежедневная работа

Для обычного полного возврата используй админ-панель: выбери платёж, проверь пользователя и сумму, укажи причину и подтверди операцию. Поддерживаются возвраты всего платежа; частичные возвраты и возврат отдельной услуги из пакета автоматически не рассчитываются.

Если ответ провайдера потерян или неизвестен, операция остаётся «возврат проверяется». Не создавай второй возврат из другого интерфейса. Бот проверяет сохранённую попытку; новая попытка с новым ключом после неопределённого ответа может стать отдельной финансовой операцией. ЮKassa гарантирует обработку повторного запроса как той же операции в течение 24 часов. В коде для повторного создания без известного ID выбран запас: после 23 часов требуется ручная сверка. [Идемпотентность ЮKassa](https://yookassa.ru/developers/using-api/interaction-format).

Возвраты из кабинета ЮKassa, банковские оспаривания и частичные внешние возвраты эта версия автоматически в журнал бота не переносит. Если такой случай произошёл, сохрани ID платежа и возврата, сверяй данные провайдера с журналом и выполняй отдельную проверяемую корректировку учёта. Не удаляй платёж и не обнуляй пользователю баланс через SQLite вручную.

Ежедневно сверяй успешные платежи, возвраты и суммы в кабинете ЮKassa с админ-панелью, проверяй выдачу чеков и обращения `/paysupport`. Делай резервные копии базы и проверяй возможность восстановления. Перед обновлением бота обязательно сохрани актуальную базу; нельзя подменять её старой тестовой копией.

## Как подтверждается оплата и что зависит от сервера

Начисление выполняется только после проверки платежа через авторизованный запрос к ЮKassa. Сверяются ID платежа, заказ, пользователь, магазин, тестовый режим, валюта и сумма; требуется успешный оплаченный статус. Запись заказа, начисление и журнал движения токенов сохраняются атомарно. Позднее подтверждение оплаты учитывается, даже если время создания нового счёта уже истекло.

В проекте используется опрос API, а не входящий webhook. После прохода по очереди процесс ждёт 30 секунд; это не обещание начисления строго за 30 секунд — длительность зависит от очереди, сети и провайдера. Есть ручная кнопка проверки. При выключенном сервере начисление откладывается до его запуска. Необработанные заказы и возвраты сохраняются в базе.

Для этого платёжного обработчика не нужно открывать входящий порт или поднимать собственный HTTPS-сервер для callback. Публичные HTTPS-страницы условий и политики всё равно нужны; их можно разместить отдельно. Адрес возврата покупателя служит для навигации и не подтверждает оплату. Веб-интерфейс покупки на собственном сайте и универсальный API продажи для сайта в эту версию не входят.

`PAYMENTS_ENABLED=false` закрывает создание новых счетов. Оно не должно мешать учесть уже состоявшуюся оплату или завершить возврат; для сверки оставляй действующие ключи соответствующего магазина. Не меняй рабочий магазин на тестовый в той же базе с незавершёнными заказами. Сохранённые запросы, ID провайдера и журнал операций нужны для восстановления после сбоев — их нельзя очищать как временные файлы.
